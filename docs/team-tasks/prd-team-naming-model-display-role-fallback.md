# PRD：团队默认命名、模型显式展示与缺失角色兜底

> 状态：产品方案（待开发实现）  
> 关联任务：TASK-001 / TASK-016  

---

## 一、问题背景

当前「项目组」功能存在以下体验缺陷：

1. **团队默认名不直观**：新团队或尚未产生有效消息的团队，在会话列表中显示为 `no messages`，用户难以识别团队用途。团队名应根据用户输入/任务内容自动生成默认名称，避免空状态列表无法辨认。
2. **角色模型不可见**：角色执行时未展示其使用的模型；创建角色时默认选项显示为「默认（跟随全局模型）」，但未明确当前全局默认模型是什么，导致用户无法判断实际模型能力。
3. **角色缺失时派活失败**：团队仅含一个角色（如只有 leader）时，leader 仍可能把任务派给「研究员」「开发」等未加入团队的角色，导致任务无人执行或流程挂起。应让 leader 在派活前感知团队现有角色，缺失时自行兜底或提示用户补全角色。

---

## 二、需求点与验收标准

### 需求 1：团队默认名称自动生成

**目标**：团队创建后，会话列表与团队详情页顶栏应始终展示一个有意义的默认名称，不再出现 `no messages` 占位文案。

**规则建议**：
- 触发时机：用户首次发送消息/任务后，若团队名仍为空或仍为默认占位，立即生成默认名。
- 命名来源优先级：
  1. 取用户第一条消息的纯文本前 N 个有效字符（去掉@、特殊符号）作为候选标题。
  2. 若第一条消息过短或为空，使用「新团队 + 创建时间」或「未命名团队 + 时间」兜底。
  3. 命名长度限制：建议 20–30 个字符，超长截断加省略号。
- 命名时机可延迟到第一条用户消息产生后，避免空标题。
- 保留用户后续手动改名的能力；自动命名不应覆盖用户已自定义的名称。

**验收标准**：
- [ ] 新团队未手动命名时，发送第一条消息后列表显示自动生成的默认名称，不再显示 `no messages`。
- [ ] 默认名来源于用户输入内容，语义可识别。
- [ ] 默认名长度受控，不撑破列表布局。
- [ ] 用户手动修改后的名称不会被自动命名覆盖。
- [ ] 老团队/已有名称团队保持现状，不受迁移影响。

---

### 需求 2：角色模型显式展示 + 默认模型解析

**目标**：在角色执行态、角色设置/创建态中，始终能看到该角色实际使用的模型名。

**规则建议**：
- **执行时展示**：角色卡片/执行 trace/顶栏等位置，在角色名旁展示当前实际模型 badge（如 `gpt-4o`、`deepseek-chat`）。
- **设置页展示**：
  - 创建角色时，默认选项不再仅显示「默认（跟随全局模型）」，而是显示解析后的全局默认模型名，例如「默认：gpt-4o（跟随全局模型）」。
  - 用户已选择具体模型时，显示所选模型名。
- **模型解析逻辑**：「跟随全局模型」应实时解析为当前全局默认模型；全局模型变更后，依赖全局的角色在 UI 上应同步显示新的解析结果（无需重新保存角色）。
- 展示信息至少包括：模型名（provider/model id 短名）；可选补充：provider 图标或标签。

**验收标准**：
- [ ] 角色执行时，UI 能直接看到该角色本次调用使用的实际模型。
- [ ] 创建角色弹窗/设置页中，默认选项展示解析后的全局默认模型名，而非模糊文案。
- [ ] 修改全局默认模型后，未单独指定模型的角色自动显示新的模型名。
- [ ] 已单独指定模型的角色，不受全局模型变更影响。

---

### 需求 3：缺失角色时 leader 不派活 + 兜底策略

**目标**：leader 拆任务后，只能把子任务分派给当前团队已存在的角色；目标角色不存在时，leader 自行处理或提示用户补全角色，避免任务悬空。

**规则建议**：
- 派活前检查：leader 在生成子任务并准备 handoff 前，获取当前团队的 agent 列表（按 id/role）。
- 缺失处理策略（推荐二选一，产品侧倾向「策略 A + 提示补全」）：
  - **策略 A（自兜底）**：目标角色不存在时，leader 将该任务并入自己的执行范围，不再 handoff 给不存在的角色；trace/消息中说明「xxx 角色未配置，由 leader 代为处理」。
  - **策略 B（提示补全）**：直接生成一条可交互提示，引导用户在团队设置中添加缺失角色；leader 暂停后续派活，等待用户操作。
- 建议优先实现策略 A，保证流程不卡；策略 B 可作为增强后续实现。
- 该检查应覆盖所有 handoff 场景（复杂任务多角色、简单任务也可能触发 researcher/developer 等角色）。

**验收标准**：
- [ ] 仅含 leader 的团队，leader 不会把任务 handoff 给不存在的 researcher/developer/tester 等角色。
- [ ] 缺失角色时，任务由 leader 继续执行或明确提示用户添加角色，流程不挂起、不报错。
- [ ] 团队后续补充缺失角色后，leader 可正常按新角色派活。
- [ ] 多角色团队若目标角色存在，派活逻辑保持原有行为。

## 三、关键决策

| 决策点 | 结论 | 理由 |
| --- | --- | --- |
| 自动命名时机 | 第一条用户消息后生成，不覆盖手动命名 | 避免空名；尊重用户自定义 |
| 自动命名来源 | 优先取用户首条消息文本，其次时间兜底 | 语义最贴近用户真实意图 |
| 模型默认显示 | 默认选项展示解析后的全局模型名 | 降低认知成本，明确实际能力 |
| 缺失角色策略 | 先实现「leader 自兜底」 | 保证流程可用、不阻塞；后续可补提示补全 |
